# Пз2 - CRUD API і валідація

Продовження вашого проєкту з Пз1. Сервер уже відповідає на `/api/health` -
тепер у нього зʼявляється сутність «нотатки на мапі»: список, читання,
створення, часткове оновлення і видалення. Дані поки живуть у масиві в
памʼяті; у Пз3 вони переїдуть у PostgreSQL, і маршрути від того майже
не зміняться.

Домен у цій роботі один для всіх - нотатки. Перевірка контракту тепер
тест на JavaScript, і він стукає саме в `/api/notes` з полями `title`,
`lat`, `lng`. Власний домен з Пз1 не знадобиться: сьогодні важлива механіка
(валідація, маршрути, обробка помилок), а не придумування сутностей.

## Як запустити

```bash
cd server
npm install
npm test
```

Сервер окремо запускати не треба: тест сам піднімає застосунок фабрикою
`buildApp()` і стукає в нього через supertest, без порта 3000 і без другого
термінала. Хочете подивитися на API очима - `npm run dev` і curl.

## Вісім перевірок

`npm test` - це не тест вашого коду, а перевірка **контракту** з лекції Л2.
Тест знає тільки домовленості: які адреси, які методи і які коди відповідей.

| # | Перевірка | Про що вона насправді |
|---|---|---|
| 1 | `GET /api/health` → `200` | сервер живий (з Пз1) |
| 2 | `GET /api/notes` → `200` | список віддається, і це обгортка `{ items, total, ... }` |
| 3 | `POST` → `201` і `id` у тілі | створення повертає створене, а не «ок» |
| 4 | `POST` з невалідним тілом → `400` | валідація є і вона на вході |
| 5 | у `400` є `details` із назвою поля | помилка каже, що саме не так - на Пз5 цей текст стане підписом під полем форми |
| 6 | `PATCH` → `200` | можна змінити частину, а не лише всю сутність |
| 7 | `GET` неіснуючого id → `404` | «немає» - це 404, а не 200 з `{"error": ...}` |
| 8 | `DELETE` → `204`, потім `GET` → `404` | видалення справді видаляє |

Тест прибирає за собою: що створив, те й видаляє. Запускати можна скільки
завгодно разів поспіль.

## Підказки

**Схеми тіла пишуться за сусідами.** `idParamSchema` і `listQuerySchema`
у тому ж файлі - готові зразки того, як виглядає zod: обмеження, дефолти,
`z.coerce`. Ваш `createNoteSchema` - те саме, тільки для полів тіла.

**`.partial()` для PATCH.** Схему для PATCH не пишуть з нуля:
`createNoteSchema.partial()` дає ту саму форму, але з необовʼязковими
полями. Одна зміна правил - в одному місці.

**Помилки кидаємо, а не повертаємо.** `throw new AppError(404, '...')` замість
`reply.code(404).send(...)` у кожному маршруті: формат відповіді описаний рівно
один раз - у `registerErrorHandler` з `lib/errors.ts`. Обробник готовий,
прочитайте його: чотири гілки, і кожна ще зустрінеться вам у Пз4.

**201 і 204 - це ви, а не Fastify.** Створення не знає, що воно «створене»:
код і тіло відповіді ставить маршрут через `reply.code(201)`. DELETE
віддає `204` без тіла - `reply.code(204).send()` і більше нічого.

**Список - обʼєкт, а не масив.** `{ items, total, page, limit }`: клієнту на Пз5
знадобиться `total`, а дописати його в готовий масив уже не вийде без ламання
контракту.

## Чого тут немає - і це навмисно

- **бази даних.** Масив у памʼяті зникає при кожному рестарті `tsx watch` -
  і це нормально: у Пз3 ви побачите різницю на власні очі;
- **автентифікації.** Поки будь-хто може створити і видалити будь-що. Автор
  і токени зʼявляться в Пз4;
- **`.env`.** Порт усе ще константа. Конфіг зʼявиться разом із базою в Пз3;
- **ESLint.** Стає вимогою в Пз7, коли лінт заїде в пайплайн. Хто налаштує
  сьогодні - не виправлятиме сімсот попереджень за вечір до здачі.
